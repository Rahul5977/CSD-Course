% ---------------------------------------------------------------------------
\section{Problem}

Given a position (\texttt{lat}, \texttt{long}), a category \texttt{cat} and a radius \texttt{rad}, return the
IDs of the 10 closest locations of that category. The assignment uses two different distances:

\begin{itemize}
  \item \textbf{Radius:} a location is valid only if its straight-line (Euclidean) distance from the query
        point is at most \texttt{rad}.
  \item \textbf{Closeness:} valid locations are ranked by the distance actually travelled on the grid.
        Links exist only between neighbouring points (no diagonals), and some links are missing.
\end{itemize}

% ---------------------------------------------------------------------------
\section{Data}

\begin{itemize}
  \item \texttt{locations.csv}: 10,000 locations forming an exact $100\times100$ grid on $[0,1]^2$ with
        spacing $1/99$, and 8 categories with 1,250 locations each. The ID of the point at row $r$ and
        column $c$ is $100r + c + 1$, where $r = 99\cdot\text{lat}$ and $c = 99\cdot\text{long}$.
  \item \texttt{link.txt}: 14,800 lines of the form \texttt{long\_A lat\_A long\_B lat\_B}. Each line joins
        two neighbouring grid points. 19,800 neighbour links are possible, so 5,000 (25\%) are missing.
  \item Every link appears only once, always with the smaller point first, so links are \textbf{two-way}.
        As an undirected graph the network is connected: every location can be reached.
\end{itemize}

% ---------------------------------------------------------------------------
\section{Choice of distance}

Because links are missing, the straight-line distance and the Manhattan distance can both be wrong about
which places are close. The distance that matches ``actual traversal distance on grid'' is the
\textbf{shortest path in the link graph}. Every link has the same length, so this is the smallest number of
links on a path, which breadth-first search (BFS) computes. This is the same idea a ride-sharing app uses: it
takes the drivers within some radius of the rider, then ranks them by driving distance on the road network,
not by straight-line distance.

\section{Algorithm}

\begin{enumerate}
  \item \textbf{Start point.} Snap the query to its nearest grid point $s$ by rounding $99\cdot\text{lat}$
        and $99\cdot\text{long}$. Points outside the square are moved to its border.
  \item \textbf{Count.} Count the locations of the category inside the circle (one numpy operation). Let
        $T = \min(10, \text{count})$.
  \item \textbf{BFS from $s$.} Each node of the right category within the radius becomes a result. When the
        $T$-th result is found at distance $d_T$, keep going until BFS reaches a node farther than $d_T$,
        then stop.
  \item \textbf{Sort.} Sort the results by (path length, straight-line distance, ID) and return the first 10.
\end{enumerate}

\paragraph{Correctness.} BFS visits nodes in increasing distance from $s$. So once it passes $d_T$, no node
it has not yet visited can be closer than the 10th result. Locations tied with the 10th are all collected
before stopping. The circle only filters the results and does not limit the search, because the shortest
path to a location inside the circle can pass outside it. Locations that cannot be reached are never
returned.

\paragraph{Complexity.} Building the graph takes $O(V + E)$ time and memory, once when the server starts
($V = 10{,}000$ locations, $E = 14{,}800$ links). A query takes $O(n_c + V' + E' + h\log h)$ time, where
$n_c = 1{,}250$ is the number of locations in the category (the radius count), $V'$ and $E'$ are the nodes
and links the BFS actually explores, and $h \approx 10$ is the number of results sorted. In the worst case
this is $O(V + E)$, but on average the BFS explores only about 116 nodes, and a query takes about 0.025\,ms.

\paragraph{Details.}
\begin{itemize}
  \item \textbf{Radius boundary:} a location exactly on the circle counts as inside. A tolerance of
        $10^{-6}$ is used because the CSV rounds coordinates to 6 decimals.
  \item \textbf{Category:} spaces are trimmed and case is ignored.
  \item \textbf{Ties:} broken by straight-line distance, then by ID, so results are always the same.
\end{itemize}

\section{API}

\texttt{GET /search/?lat=\&long=\&cat=\&rad=} returns the 10 IDs, closest first. \texttt{/search} without
the trailing slash also works. Missing or invalid parameters return HTTP 400 with an error message.

\begin{lstlisting}[language={}, numbers=none]
$ curl 'http://10.1.75.53:3270/search/?lat=0.74&long=0.6&cat=bank&rad=0.1'
{"ids":[7160,7059,6862,7167,7267,7067,6459,7454,6656,6953]}
\end{lstlisting}

Adding \texttt{\&debug=1} also returns, for each result, the path length, the straight-line distance and the
path itself. The server also has a demo page at \texttt{\api/} that draws the links, the radius and the
paths to the results (Figure~\ref{fig:demo}).

\section{Testing}

\begin{itemize}
  \item On 1,600 random queries (on and off grid points, all categories, radii from 0.02 to 2) the API
        returns exactly the same ordered list as a brute-force Dijkstra search over all 10,000 points.
  \item A small $3\times3$ grid with a missing link checks the exact detour order. Unreachable points are
        never returned.
  \item Edge cases: a point exactly on the circle, the corners, points outside the grid, and fewer than 10
        valid locations.
  \item API tests check the route and parameter names, the response format and the errors for bad input.
        All 21 tests pass.
  \item A query takes about 0.025\,ms inside the server. There were no errors in a 5,000-request load test
        against the deployed API.
\end{itemize}
